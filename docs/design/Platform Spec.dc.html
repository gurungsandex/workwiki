1. Architecture and stack

One process, one database, one object store. Everything a small company needs to evaluate the product runs from a single docker compose up. The bias throughout is toward fewer moving parts than toward best-in-class components, because every extra service is a self-host that fails on the first attempt.

Shape

A single server-rendered application. Employee reads are access-filtered on the server, so no client ever receives content it is not entitled to and then hides it. Admin authoring is a client-heavy island inside the same app, talking to the same route handlers the public API exposes.

2. Data model

The schema is content-agnostic by three devices, and by nothing else:

  1. Dimensions are rows, not enums. Department, role, employee type and location are tables an admin populates. No CHECK constraint, no TypeScript union, no migration ever names a real one. The single exception is employee_type.kind, a soft hint (salaried | hourly | contingent | other) used only to pick sensible defaults in the rule builder.
  2. Sections are data. There is one section table. A "built-in" section is a row inserted by the scaffold seeder, distinguishable from a custom one only by origin = 'scaffold', which no query branches on. There are no section subtypes and no code path may test a slug.
  3. Specialised content is a block kind, not a table hierarchy. block.kind selects a validator and a renderer; the typed payload lives in block.data (JSONB, validated per kind). Adding the eligibility-checker block adds a validator and a component, not a migration.

Indexes worth naming

  • page_search: GIN on to_tsvector of title + flattened block text, plus a gin_trgm_ops index on title for fuzzy match.

3. Access control

One pure function, one place. Signature:

evaluate(subject: Subject, node: Node, at: Date): Decision

Subject  = { departmentId, roleId, employeeTypeId, locationId,
             anchors: Record<string, Date>, groupIds[], userId }
Decision = { allowed: boolean,
             visibility: 'full' | 'teaser' | 'preview' | 'hidden',
             unlockAt: Date | null,
             reason: { ruleId, clause } | 'inherited' | 'no-rule' }

Nothing else in the codebase reads access_rule. The UI, the search query, the PDF export and the assistant's retriever all call this — search and retrieval by way of a generated SQL predicate compiled from the same rule rows, tested against the function for agreement on every rule shape.

Evaluation order

  1. Resolve the ancestor chain, root-first. Evaluate the parent decision before the child; a child can only narrow it. Access narrows down the tree — never widens.
  2. At each node: if it has no rules, inherit the parent decision verbatim.
  3. Conditions inside a rule are ANDed; values inside a condition are ORed. A condition set to "any" or omitted always matches.
  4. Any matching deny short-circuits to hidden, regardless of allows, at that node or any ancestor.
  5. Otherwise the node is allowed if any allow rule matches, intersected with the parent's allowance.
  6. If every condition matches except tenure, the node is locked, not denied: return allowed: false with visibility from the rule (default teaser) and the computed unlockAt. This distinction is the product.
  7. Return the rule id and the clause that decided it. The preview tool renders it as a sentence.

Tenure and date arithmetic

Offsets are structured, never a day count: { anchor, unit: day|week|month|year, value, then?: 'first_of_next_month' }. The then modifier is what makes real benefits eligibility expressible — first of the month following hire date + 60 days — and it composes after the offset, not before. All arithmetic runs in the location's timezone at local midnight; a rule must not unlock a day early for a west-coast employee. Month arithmetic clamps (31 January + 1 month = 28 February).

Worked example

Subject: part-time employee, Clinical Operations, New Jersey, hired 15 January, evaluated on 1 March. Target: page Retirement plan enrolment, whose parent topic Retirement allows full-time and part-time in NJ or NY with no tenure condition, and whose own two rules are:

RuleEffectConditionsLocked visibility
R1allowemployee_type ∈ {full_time}; location ∈ {NJ, NY}; tenure ≥ 90 days from hire_dateteaser
R2allowemployee_type ∈ {part_time}; hours_per_week ≥ 20; tenure ≥ 12 months from hire_date, then first of next monthteaser

Parent: allowed, full. R1: employee_type fails — no match, discarded. R2: type matches, hours match (24), tenure fails — 15 January + 12 months = 15 January next year, then first of next month = 1 February of the following year. Every non-tenure condition matched, so rule 6 applies.

{ allowed: false, visibility: 'teaser', unlockAt: '<next year>-02-01', reason: { ruleId: 'R2', clause: 'tenure' } }

The employee sees the page title, the unlock date, and the one-line teaser — never the body. The admin's preview tool renders the reason as: "Locked for this person by the rule 'Part-time employees working 20+ hours, one year after hire, from the first of the following month'. Unlocks 1 February."

Benefits eligibility

Same function, richer return: { eligible, eligibleOn, enrollmentOpens, enrollmentCloses, windowState }. The enrolment window is expressed relative to eligibleOn or to a fixed annual date, so open enrolment and new-hire windows use one mechanism. The employee sees their own dates; there is no generic eligibility table in the employee UI.

The condition builder

No JSON reaches the admin. Rows of dropdowns compose into a rendered sentence updated live — "Full-time employees in NJ or NY, 90 days after hire" — with a live count of how many current employees the rule matches and a one-click jump into preview-as for any of them. Rejected: a JSON textarea with schema validation — faster to build, unusable by an HR lead.

4. Import and extraction pipeline

Five stages, each resumable, each leaving an artefact the admin can inspect. Nothing publishes; nothing is discarded.

Classification proposals

Signal detectedProposed as
Heading hierarchySections and pages, mapped to existing ones where titles fuzzy-match above threshold
Repeated name / email / phone triplesContact cards, deduplicated against existing cards by email
Table with a "reports to" or "manager" columnOrg chart nodes and edges, with unresolved parents flagged
Numbered or "Step 1…" procedureStep-by-step guide draft, with the last step flagged as missing a handoff
Waiting period phrasing ("after 90 days", "first of the month following")Benefit with the tenure offset pre-filled — the parse shown for confirmation, never applied silently
An effective date or version linePolicy page with effective_date set and acknowledgment suggested
Long legal prose over a length thresholdSource block plus an empty summary block queued for authoring — the platform never machine-writes a published summary

Every item carries a confidence score; the review queue sorts low-confidence first, and OCR pages under a mean-confidence floor are marked needs a human read rather than imported as text. An empty extraction is a failure, reported as one. Re-importing a document already in the batch history offers a per-item diff against what was accepted last time — accept the change, keep the current version, or fork — never a silent duplicate. After review, imported content is indistinguishable from hand-authored content: same editing, same versioning, same rules.

Employee, week one

Arrives on a phone, often before any company laptop exists. Lands on the personalised home; sees two outstanding acknowledgments and that a department playbook unlocks on day 30. Reads a policy: summary, key points, who to ask, source one click deeper. Acknowledges — timestamped against the exact version. Searches "when do I get insurance", gets their own eligibility date rather than a table, and a step-by-step guide whose final step hands off to the carrier's enrolment site with the domain shown. Checks steps off for themselves, with the label making clear that nothing was submitted.

Employee, month six

A life event. Searches "parental leave". Gets a branched guide: their state, their employee type, the company steps and the state agency steps visually distinct. Follows the external handoff, exports the page to PDF for a clinic appointment, and lands on the resolved HR contact card with response-time expectation shown. Nothing here required asking a human first — but the human is named on every screen.

Admin, ongoing

Weekly: the failed-search list (the content-gap list), the issue-report queue, content health checks, outstanding acknowledgments. Publishing a new policy version automatically re-triggers acknowledgment for everyone in scope. A delegated department sub-admin edits their own playbook and nothing else.

8. UI/UX direction

Information architecture

Search is the primary navigation; browse is the fallback. The employee shell is four destinations — Home, Browse, My things (benefits, timeline, acknowledgments, bookmarks), Help (contacts and external resources) — plus a persistent search affordance and, if enabled, the assistant. Depth is capped at section → topic → page; a fourth level is a signal the content should be split, and the editor says so.

Interaction patterns

  • Progressive disclosure as a fixed page order. Summary, key points, guidance, who to ask, source. The same five beats on every long document, so the shape becomes learnable.
  • Locked ≠ absent. Locked items render in place with title, unlock date and teaser, styled as anticipated rather than forbidden. Knowing what is coming is core value.
  • Internal versus external is a visual language, not a word. Internal steps and cards sit on the paper ground; external handoffs take the second accent, the destination domain, an external-link mark and a last-verified date. One glance answers "does clicking this leave the company?"
  • Summary labelling is persistent and inline. Every summary carries an admin-editable note that it is a plain-language summary, that the linked source governs, and the resolved contact card rendered inline — not a footer.
  • Personal checklists say so. Checking a guide step shows "for your own tracking — this notifies no one and submits nothing" next to the control, not in a tooltip.
  • Editing in context. The admin edits inside the employee layout with a preview toggle, autosave and a visible save state; no disconnected back office.

Visual system

Broadsheet: near-black serif on paper white, hierarchy from the type scale and whitespace rather than boxes and rules. Reading measure held at 65–75 characters. Cyan for interactive elements, magenta reserved for the rarer second signal — here, external handoffs. The company's logo and accent are set at setup and override the accent token; light and dark themes both ship. Motion is subtle and purposeful, and respects prefers-reduced-motion.

Mobile and accessibility

Phone layout is designed and tested first: one-handed reach, 44px minimum targets, bottom navigation, installable as a PWA with published content cached for offline reading. WCAG 2.1 AA is verified, not assumed — automated axe checks in CI, keyboard traversal of every flow, real focus rings, screen-reader-correct landmarks and heading order, and alt text enforced at upload time rather than requested.

10. The optional AI assistant

Off by default, disableable, and load-bearing for nothing. No other feature may call into it. The highest-severity failure in the system is an employee learning the contents of a locked page through the assistant, so the access filter is applied to retrieval, in SQL, before any text reaches a model — never by instructing the model.

flowchart TD
  Q["Employee question"] --> AC{"Enabled and under cap"}
  AC -->|no| OFF["Feature absent, or capped notice"]
  AC -->|yes| RET["Compile access predicate, then retrieve
published and permitted chunks only"]
  RET --> HIT{"Retrieved and cited"}
  HIT -->|no| HAND["Nothing on that, plus resolved contact card"]
  HIT -->|yes| ANS["Answer, sources, summary label, who to ask"]
  HAND --> LOG["Log questions and gaps into analytics"]
  ANS --> LOG

The model call sits between retrieval and the citation gate: content is delimited as data, and a response whose citation ids are not all in the retrieved set is discarded and replaced by the handoff.

Rules it operates under

  • Answers only from published content in this instance. It does not answer general employment-law questions, and it does not answer from model knowledge.
  • Uncited answer is a bug: the response is discarded and replaced with the handoff. Enforced by post-generation validation of citation ids against the retrieved set, not by prompt wording.
  • It restates and locates. It does not interpret law, compute a legal deadline, weigh benefit options, or say what an employee is owed. Any date it states — an eligibility date, an enrolment window — comes from the evaluator's output injected as a fact, never from model arithmetic.
  • Retrieved content is data, delimited and never instruction. Tested with a document containing injected instructions as a standing regression case.
  • Provider is admin-supplied and can point at a local model. The platform ships with no credentials and makes no call until configured. Usage estimate and a monthly call cap are visible in admin.
  • Questions and unanswered questions feed the same analytics as failed searches — the content-gap list. Per-answer feedback lands in the admin queue beside page reports.

PasswordsArgon2id with tuned parameters recorded in config; rehash on login when parameters change. Breach-list check on set, minimum length over composition rules.
SessionsOpaque 256-bit tokens, hashed at rest, HttpOnly; Secure; SameSite=Lax; sliding expiry with absolute cap; per-session device and last-seen for the admin view; revocation is a delete.
Brute forcePer-account and per-IP limits with progressive delay on login, reset and invite redemption. Failure messages never reveal whether an address exists.
UploadsType sniffed, not trusted from extension; size capped; stored outside the web root under random keys; served only through the access-checked route; ClamAV scan in the worker where available; PDFs and images rendered in a sandboxed viewer with no active content.
PIIPersonal contact details, hire dates and eligibility status are the sensitive set. Field-level visibility enforced in the serialiser — the single place responses are built — so no route can leak a mobile number by forgetting a filter. Excluded from logs, audit diffs and error reports. Never present on an unauthenticated response.
AuthorisationOne evaluator, called server-side. Admin scope checked per target, not per route group. Preview-as contexts are read-only and cannot mutate or acknowledge.
Transport and headersHTTPS assumed and documented behind a proxy; HSTS, strict CSP with nonces, no inline event handlers, frame-ancestors none.
Data at restDisk encryption is the deployment's responsibility and is documented; TOTP secrets are encrypted with a key from the environment. Full-database encryption is not claimed.

13. Open questions and risks

Questions that would change the architecture

  1. Does an employee ever need to see another employee's eligibility or acknowledgment status? If managers need team completion views, the access model gains a second axis (subject-about-subject) and the org chart becomes load-bearing for authorisation, not just navigation. Assumed no for now.
  2. Is content ever multilingual? Per-locale page versions are cheap to design in now and expensive to retrofit, because acknowledgment must attest a specific language version. Assumed single-language.
  3. Who owns "location"? Work state drives jurisdiction, but remote employees have a work state that differs from the site. Modelled as location on the profile with an optional distinct work_state; confirm whether both are needed.
  4. Does acknowledgment need to be legally defensible evidence? If yes, the attestation record needs a hash chain or external timestamping, not just a database row. Currently: version hash plus append-only audit.
  5. Expected scale of the first adopter — a few hundred or a few thousand employees changes worker sizing and whether OCR belongs in the web container.
  6. Is a manager tier really out of scope? Field-level visibility already says "visible to managers", which is a role-like distinction inside a two-tier model. Currently derived from the org chart rather than a third tier — confirm that holds.

Assumptions made without asking

  • English-only content, one timezone default with per-location overrides.
  • Employees have an email address the company can reach; invite-by-link covers those who do not yet.
  • Acknowledgment is an internal attestation only, with no external legal filing character.
  • No manager tier; manager-visible fields resolve from the org chart.
  • Sample content ships as a clearly labelled demo set, removable in one action, containing no live external URLs.
